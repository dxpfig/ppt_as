# MiniMax M3 上下文误拦截修复

## 根因与复现

用户任务 `610a9ef27fed44a6a74a8141c7a72092` 在规划阶段被本地预算检查拦截，尚未发送生成请求。输入是“AI生成PPT速度优化方案，请帮我生成个汇报文件”，新建、5 页、工作汇报、现场演讲。原检查点保存场景选择，尚无已完成页面。

切回 MiniMax 后，模型列表 `/v1/models` 和详情 `/v1/models/MiniMax-M3` 均仅提供模型标识、时间与归属，没有上下文窗口字段。因此既有机制使用 128000 的回退窗口，预留输出 32000、安全余量 4000，可用输入为 92000。

旧适配在没有 vLLM `/tokenize` 时将完整 JSON 的 UTF-8 字节数用作 token 保守上界。本次请求的 142307 是这个字节上界，不是 MiniMax 实际输入 token 数；错误文字却没有标明估算性质。

从原请求及检查点重建完整规划输入，保持规则和数据原样，用官方计数接口 `POST /v1/responses/input_tokens` 验证：服务端返回 34388。加上 Chat `name` 字段的保守字节余量 66 后，预算计入 34454，能够通过现有 92000 限额。

## 修改

- OpenAI 兼容服务在 auto 模式下继续优先读取模型能力及 vLLM 分词器；没有分词器时，用合成短文本自动探测同源标准 Responses 计数接口。不按 MiniMax 名称写死窗口或能力。
- 计数请求转换完整消息、图片、工具声明和工具调用记录。消息名称计入额外保守余量；未知字段与不支持的媒体明确报错，不能静默丢弃后少计输入。
- 使用完整原请求作为缓存键，生成前和 AgentScope 上下文检查共用计数结果；内容或消息名称变化重新计数。
- 计数请求禁止重定向。能力探测不支持时保留明确标记的保守回退；已发现的计数服务出错或返回非法计数时阻止提交。更小的模型窗口及输出预留约束继续生效。
- 超限提示区分“服务端估算”“保守估算上界”“回退窗口”，并消除原提示末尾的双句号。

完整 Kimi 规则、源文档、修复预算和视觉发布门禁未作修改。模型保持 MiniMax-M3。

## 窗口边界

[官方模型文档](https://platform.minimax.io/docs/guides/text-generation)列出 M3 的上下文窗口为 1,000,000；[官方模型介绍](https://www.minimax.io/models/text/m3)说明最高 1M、至少保证 512K。但当前 API 未公布该账号/路由的窗口元数据，本次保留 128K 保守回退。恢复成功不代表已验证 1M 输入，也不代表整稿视觉审稿已通过。

[计数接口文档](https://platform.minimax.io/docs/api-reference/responses-input-tokens)将结果定义为服务端输入 token 估算。程序继续保留安全余量，不将协议转换后的计数描述为无误差的精确测量。

诊断目录：`runtime/diagnostics/minimax-context-2026-10-10/`，包含修改前代码、官方文档快照、API 能力响应、原请求复现输入、计数证据与 `studio-tests.log`。运行时目录仅供本机诊断。
