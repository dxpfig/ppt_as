# 生成架构重构基线

## 决策

保留快速模式和专家模式两个产品入口，但内部采用“一个生成平台 + 两种 Execution Policy”。

两种模式共享：

- 项目、文档 revision 和版本存储
- 上下文、模板、参考资料、知识库和研究服务
- 模型访问、限流、预算和检查点
- 页面状态、渲染、结构校验和导出
- 视觉审稿和修复安全约束

两种模式只在以下方面不同：

- 规划和页面生成方式
- 批次与迭代预算
- 视觉审稿深度
- 自动修复和交付策略

## 当前落地

`agent_service/execution_policy.py` 是第一步，集中读取快速/专家模式的默认参数并做边界校验。

- 快速模式：配置页面并发和最终审稿导出。
- 专家模式：配置批次、Agent 迭代、规划尝试、结构修复和布局修复预算。

后续重构应让 Orchestrator、页面队列和资源池读取同一 Policy 对象，避免各模块直接散读环境变量。

`agent_service/orchestrator.py` 已集中负责执行路线判断，`app.py` 不再自行组合页面操作、专家、旧版和快速路线的优先级。

`orchestrator.py` 同时定义了统一任务状态、允许的迁移和阶段顺序；`app.py` 在更新任务状态前执行迁移校验，`job_execution.py` 复用同一阶段定义。

`agent_service/render_service.py` 已承载共享单页渲染、页面问题过滤和浏览器证据输出。

新增共享服务边界：

- `page_work_queue.py`：页面生命周期和有界并发。
- `review_service.py`：快速、专家和页面操作共用视觉审稿入口。
- `repair_coordinator.py`：问题指纹、停滞判断和分批修复。
- `export_service.py`：最终交付导出的统一边界。

- `model_gateway.py`：文本/视觉模型、健康检查和超时配置的统一入口。
- `context_service.py`：模板参考和研究资料的统一入口。
- `resource_manager.py`：模型、渲染和导出三个独立并发池。
- 渲染缓存键：页面内容、文档主题/尺寸、媒体哈希和渲染器版本。
- 审稿缓存键：页面图像、文档/页面语义、视觉模型、场景、用途和规则版本。
- 相同问题指纹再次出现即停止修复，防止无进展循环。
- 交付导出缓存键：文档版本、媒体哈希、Chromium 和渲染器版本。
- 专家模式浏览器验证、对比度检查和视觉门禁已从 `kimi_agent.py` 抽到 `kimi_validation.py`。
- 公司模板封面/背景/标识与自适应布局已抽到 `kimi_template.py`。
- 页面生成、视觉审稿、修复批大小、自动适配和导出修复预算统一由 `ExecutionPolicy` 提供。
- 页面 lifecycle 已进入快速生成和视觉交付检查点，任务恢复后可观察每页状态。
- 渲染、审稿和导出缓存使用唯一临时文件或整目录原子发布，并发任务不会读到半成品缓存。

4. 生成、审稿和导出使用独立资源池：已完成。
5. 页面问题使用稳定指纹和停滞检测：已完成。
6. 两模式共享渲染、导出和版本发布路径：已完成。

## 迁移与回滚

- 本轮没有修改 PPTD 文档格式、项目目录或任务持久化 schema，已有项目无需迁移。
- 旧路线保留在 `orchestrator.py` 的兼容分支中；新共享服务按任务逐步接管，不要求一次性切换所有历史任务。
- W12 开始前的检查点是 `9515ca6`，共享服务检查点是 `2dd2c7f`。代码回滚不会删除项目、版本或导出文件。
- `PPT_RENDER_CACHE=0`、`PPT_EXPORT_CACHE=0` 可立即关闭对应缓存；视觉审稿可用 `PPT_KIMI_VISUAL_REVIEW=0` 关闭专家路线门禁。
- 缓存位于运行数据的独立目录，可随时删除并由下一次任务重建，不属于权威文档版本。
- 回滚代码后，已有检查点仍按原有 revision、候选稿和视觉审稿凭证校验；不兼容或来源不一致的检查点会被拒绝，而不是覆盖原稿。

## 不变量

- 任何失败或取消都不能发布未完成产物。
- 文档 revision 冲突必须拒绝覆盖。
- 修复不得改变正文、数据、公式、图表值和来源。
- 最终 PPTX、PDF 和预览必须来自同一 revision。
- 模式差异不能复制渲染、审稿和导出实现。
- 重构每一步必须通过 W08-T0 的快速测试和契约测试。
