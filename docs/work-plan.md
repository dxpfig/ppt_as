## W04：单页修复、AI 视觉检视和设计

目标：让用户能针对当前页执行独立操作，不影响其他页面。

进度：已完成。

- 新增页面任务类型 `page-repair`、`page-review`、`page-design`。
- 新增页面级渲染、机械排版检查、AI 视觉审稿、修复和重新设计服务。
- 修复和设计通过版本冲突保护提交新版本，未选页面保持不变。
- 当前页预览下方已增加“页面修复”“AI 视觉检视”“设计”三个按钮。
- 设计按钮打开悬浮对话框，完成后保存为新版本并可从版本记录恢复。
- 后端页面操作和任务路由测试已通过。
- 页面操作专项浏览器契约测试已通过，覆盖当前页参数和设计对话框提交。
- 设计完成后先保存私有候选稿，返回页面预览以及应用、放弃接口。
- 应用设计稿时校验基础 revision，确认后才提交新的文档版本。

界面要求：

- 在文档存在时的页面预览工具栏或预览区域底部提供三个按钮：
    - 页面修复
    - AI 视觉检视
    - 设计
- “设计”打开悬浮对话框，用户输入设计想法。
- 所有按钮在页面没有生成完成、任务运行中或文档版本冲突时应有明确状态。
- 任务执行时显示进度、失败原因和停止入口。

功能要求：

- 页面修复：使用现有结构、排版、浏览器渲染和导出规则检查当前页，修复已定位的问题；默认不修改正文和数据语义。
- AI 视觉检视：渲染当前页并调用视觉模型，只返回问题、证据和修复建议，不直接覆盖文档。
- 页面设计：结合当前模板、设计要求、当前页内容和用户提示生成新的布局与表达。

数据与安全要求：

- 每个操作携带当前 `expectedRevision`，防止覆盖并发修改。
- 修复和设计先生成候选稿，通过结构与导出检查后再提交新版本。
- 设计候选稿支持预览、应用和放弃。
- 修复流程保持文字、数据和资源来源不变，除非用户明确要求修改内容。
- 所有操作复用现有任务、SSE、检查点和版本恢复能力。

验收标准：

- 三个操作可分别作用于当前页。
- 失败不会破坏当前文档，成功会生成新的文档版本。
- 页面修复和设计候选稿通过结构、渲染及导出检查。
- AI 视觉检视结果可以定位到具体页面和元素。
- 并发修改时能正确返回版本冲突并提示重新加载。

## W07：断网、内网和完全隔离模式调试

目标：明确不同网络环境下的可用能力和降级行为。

计划模式：

| 内网离线模式 | 本地模型、公司知识库和内网文件服务 | 不访问公网            |

工作内容：

- 盘点所有公网依赖，包括模型、视觉模型、图片搜索、Web 研究、字体和外部素材。
- 为 MiSans、STIX 和中文字体提供本地包或可验证缓存。
- 准备本地 Chromium、LibreOffice、Docker 渲染镜像和字体。
- 公网搜索关闭时只使用本地知识库、用户资料和本地缓存。
- 健康接口和前端显示模型、视觉、知识库、搜索、字体和渲染器状态。
- 测试冷启动断网、运行中断网、DNS 不可用和仅有内网服务等场景。

验收标准：

- 内网离线模式可以完成生成、修复、视觉检视和 PPTX/PDF 导出。
- 完全隔离且无配图时，能够生成并导出文字型 PPT，并明确提示素材能力受限。
- 外部服务不可用不会导致页面误报成功或伪造引用。
- 部署包中所有必需字体、渲染器和镜像有明确来源及版本。

## W08-T0：重构前测试与性能基线固化

目标：在性能和架构重构前建立可重复、可执行的行为契约，确保重构不会改变用户可见功能、文档数据安全、导出能力以及快速/专家两种模式。

测试固化是性能优化和架构重构的进入条件，不是重构完成后的补充工作。

### 当前测试基础

- 当前约有 39 个 Python 测试模块和 403 个 Python 测试方法。
- 当前有 10 个 Node/浏览器测试文件。
- 已有 PPTD 存储、生成、导出、视觉修复、模拟 Agent 和任务恢复等测试。
- 根目录 `test:studio` 当前只显式运行部分 Python 测试模块，没有覆盖全部测试模块。
- 前端 `package.json` 尚无正式测试命令。
- 根目录尚无统一的 `pnpm test` 聚合入口。
- 浏览器、真实模型、真实渲染和离线环境测试尚未形成统一的必跑与可选测试分层。

### 测试分层

计划建立以下测试入口，命令名称可在实施时调整：

```bash
pnpm test:fast        # 单元、纯函数和前端状态模型
pnpm test:contract    # API、任务、文档、模式和错误契约
pnpm test:browser     # 前端交互、iframe、SSE 和页面状态
pnpm test:integration # Chromium、LibreOffice、PPTX/PDF 实际导出
pnpm test:live        # 真实模型、本地 Qwen、公司知识库
pnpm test:perf        # 固定样例的阶段耗时和调用次数
pnpm test:all         # CI 可稳定执行的完整集合
```

- 快速和契约测试必须不依赖真实模型或外部公司服务。
- 真实模型、知识库和离线服务测试必须显式区分，不能混入默认不稳定测试集。
- 测试失败时应输出足够定位问题的任务 ID、阶段、页面和断言，不输出密钥或完整敏感资料。

### 必须固化的契约

| 层级     | 固化内容                                     | 不固化内部实现                   |
| -------- | -------------------------------------------- | -------------------------------- |
| API      | 请求、响应、错误码、SSE 事件和 revision 规则 | 路由内部调用顺序                 |
| 任务     | 排队、运行、取消、失败、恢复、幂等和并发冲突 | 状态保存在哪个私有函数           |
| 页面     | 页面 ID、元素 ID、顺序、内容和语义保护       | YAML 的具体序列化字节            |
| 模板     | 封面、致谢、背景、公司标识和正文页规则       | 宿主处理函数如何拆分             |
| 视觉审稿 | 问题定位、严重级别、通过/失败和修复边界      | 提示词的全部字符串               |
| 导出     | PPTX/PDF/预览来自同一 revision，文件可打开   | PPTX ZIP 内部文件顺序            |
| 模式     | 快速和专家模式都能通过各自入口完成生成       | 两个模式是否使用同一个 Python 类 |
| 降级     | 模型、知识库、渲染器不可用时的明确错误或降级 | 错误经过哪个内部模块包装         |
| 性能     | 阶段耗时、调用次数、重试次数和资源使用基线   | 每次执行耗时完全相同             |

不得把以下实现细节固化为阻塞重构的精确快照：

- 完整系统提示词文本。
- Agent 的 ReAct 迭代次数。
- 私有函数名称和调用次数。
- 日志文案的精确标点。
- 与字体和 Chromium 版本相关的逐像素截图。
- 随机 ID、临时文件名和文件时间戳。

### W08-T0.1：统一测试入口

- 补齐根目录、前端和后端的统一测试命令。
- 让默认测试命令发现全部应运行的测试模块。
- 区分快速、契约、浏览器、集成、真实服务和性能测试。
- 为 CI 设置明确的超时、重试和日志保留策略。
- 真实模型测试使用显式开关，不允许默认触发付费或外部服务。

### W08-T0.2：API 和任务生命周期契约

固化以下行为：

- 快速模式和专家模式的请求及 `kind` 路由。
- `queued → running → completed/failed/cancelled/interrupted` 状态。
- SSE 事件结构和阶段字段。
- `expectedRevision` 冲突返回 409。
- 同一项目不能同时运行冲突任务。
- 取消任务后不能发布旧产物。
- 失败后不能生成可下载的 artifact metadata。
- 重试和恢复不会重写已完成页面。
- 服务重启后任务状态和检查点可恢复。

### W08-T0.3：生成领域不变量

验证所有生成路线都满足：

- 最终文档是 PPTD v2。
- 页面路径与主文档声明完全一致。
- 页面和元素 ID 唯一。
- 单页修改不会改变未选择的页面。
- 视觉修复不能替换正文、数据、图表值、公式和来源。
- 模板封面、致谢、背景和公司标识规则一致。
- 公司模板分析素材不能冒充生成结果。
- 不伪造数据、来源、URL 或本地资源。
- 生成失败时保留原稿和检查点，不覆盖可交付版本。

### W08-T0.4：黄金测试集

## W08：优化 PPT 生成速度

目标：在保证交付质量的前提下，将当前约一小时的生成时间显著降低。性能优化分为两部分：

- W08-T0 先建立回归测试、黄金样例集和性能基线。
- W08 完成低风险、可快速验证的重复计算消除和调度优化。
- W12 完成统一编排主干、共享服务和快速/专家执行策略的结构化重构。

### 已确认的架构方向

“快速模式”和“专家模式”作为两个产品入口继续保留。架构上不维护两套互相复制的生成实现，而是采用：

> 一个共享生成平台 + 两种执行策略（Execution Policy）。

两种模式共享上下文、模型访问、页面状态、渲染、校验、视觉审稿、版本管理和导出能力；仅在规划方式、页面生成方式、审稿深度和修复预算上采用不同策略。

目标结构：

```text
Studio UI
  → Job API / SSE
  → Generation Orchestrator
      ├─ Quick Execution Policy
      ├─ Expert Execution Policy
      ├─ Context Service
      ├─ Model Gateway
      ├─ Page Work Queue
      ├─ Render Service
      ├─ Validation Service
      ├─ Visual Review Service
      ├─ Repair Coordinator
      ├─ Document Store
      └─ Export Service
```

### 当前需要解决的主要性能瓶颈

- 专家模式修复少量页面时仍反复渲染整份文档。
- 浏览器排版检查、页面截图和视觉审稿之间存在重复渲染。
- 视觉审稿当前逐页串行执行，等待模型时没有充分利用并发能力。
- 快速模式在视觉审稿前生成原生 PPTX，审稿结束后又执行一次完整导出。
- 导出任务占用 `LLM_LIMIT` 模型并发槽，导致不需要模型的导出阻塞生成任务。
- 专家模式缺少页面问题是否真正减少的判定，可能对同一组问题持续修复。
- 页面批次、页面并发和视觉审稿并发使用固定默认值，不能根据模型和限流动态调整。
- 模板转换、页面渲染、视觉审稿和最终导出没有统一的内容哈希缓存。

现有任务记录已证实性能波动：

- 有 Kimi 任务准确运行约 5401 秒后触发 5400 秒任务上限。
- 有 Kimi 任务运行约 4756 秒后失败。
- 一项 32 页任务约 1938 秒完成，但保留 4 项排版问题。
- 一项 27 页任务约 1793 秒完成，但保留 125 项排版问题。

### 双模式策略

| 能力       | 快速模式                 | 专家模式                       |
| ---------- | ------------------------ | ------------------------------ |
| 规划       | 一次结构化规划           | 规划 Agent 与设计导演          |
| 页面生成   | 并发结构化页面生成       | 页面 Agent 使用文件与检查工具  |
| 设计一致性 | 共享页面模板和设计 token | 先确定设计系统，再并行创作页面 |
| 校验       | 批次校验和最终整稿校验   | 页面批次校验和最终整稿校验     |
| 视觉审稿   | 整稿总览加风险页面       | 整稿及页面级审稿               |
| 修复       | 一到两轮定向修复         | 多轮专家修复，必须有停止条件   |
| 主要目标   | 尽快得到可用文档         | 质量优先，同时设置软硬时间预算 |
| 导出       | 审稿通过后一次导出       | 用户确认或策略触发后一次导出   |

### 页面状态和增量处理

每个页面采用稳定状态：

```text
planned
  → generated
  → structurally_valid
  → rendered
  → reviewed
  → repaired
  → approved
```

每个页面记录：

- 页面内容哈希。
- 渲染图片哈希。
- 当前问题列表。
- 已尝试修复次数。
- 最后一次有效修改时间。
- 是否阻塞最终交付。

修复和审稿只处理尚未达到 `approved` 的页面。

### 渲染与导出优化

- 建立增量渲染缓存，缓存键至少包含页面内容哈希、主题与字体哈希、画布尺寸、浏览器版本、前端渲染器版本和模板资源哈希。
- 页面修改后只重新渲染变化页面；整稿 PDF 和预览在里程碑阶段生成。
- 将视觉审稿渲染和最终交付导出拆成两个操作：
    - `render_for_review`：浏览器 PDF、页面 PNG 和布局测量。
    - `export_delivery`：原生 PPTX、最终 PDF、页面预览、源文件和导出报告。
- 视觉审稿期间不生成原生 PPTX，审稿通过后只执行一次最终导出。
- 把生成、视觉审稿、渲染和导出拆成独立并发池，导出不能占用模型并发额度。
- 复用 Chromium 进程、模板转换结果和已导出且内容未变化的交付物。

### 视觉审稿优化

- 整稿总览先执行一次，再按页面分组进行受控并发审稿。
- 默认页面审稿并发从 2–3 路开始，根据 429、延迟、模型队列和显存使用动态调整。
- 未变化页面复用上一次审稿结果。
- 视觉能力探测结果按模型端点缓存，避免每次任务重复检查图片识别能力。
- 快速模式只对高风险或变化页面执行页面级高清审稿，专家模式执行完整页面审稿。

### 修复停滞控制

每个问题建立稳定指纹：

```text
页面路径 + 元素 ID + 问题码 + 内容哈希
```

出现以下情况时停止继续修复：

- 连续两轮问题集合完全一致。
- 修改前后页面内容哈希没有变化。
- 问题数量没有下降，且新增问题超过已修复问题。
- 单项问题达到尝试次数上限。
- 已超过阶段软时间预算。

停止修复后进入“可编辑但有警告”状态，保留未解决问题和检查点，不能继续无上限消耗时间。

### 模型、上下文和并发优化

- 建立固定主题、模板、页数和资料规模的基准测试集。
- 记录规划、页生成、素材检索、修复、视觉审稿和导出各阶段耗时。
- 统计模型调用次数、token 数、重复上下文、重试次数和并发水平。
- 减少规则、规划和已完成页面在请求中的重复序列化。
- 模板、规则和参考资料按内容哈希缓存。
- 稳定系统提示保持固定前缀，利用本地 Qwen/vLLM 前缀缓存。
- 页面 Agent 只读取当前页面相关章节，减少完整历史重复发送。
- 页面批次优先共享设计系统和已有代表页，不重复发送大段历史。
- 根据模型上下文、429、延迟和失败率动态调整页面批大小。
- 对独立页面使用受控并发，并限制模型限流和内存峰值。
- 本地 Qwen 的生成并发与模型服务 continuous batching、GPU 和显存能力匹配。
- 使用检查点恢复，避免重跑已完成页面。
- 同时测试远端模型和本地 Qwen，分别给出性能基线。

### 渐进式预览

- 快速模式完成页面批次后生成草稿预览，降低用户感知等待时间。
- 明确区分 `draft`、`reviewed` 和 `exported` 三种状态。
- 草稿可以查看，但不能冒充通过最终审稿的交付物。

### 性能观测指标

每个任务至少记录：

- 排队等待时间。
- 首个页面出现时间。
- 可编辑 PPTD 完成时间。
- 视觉审稿完成时间。
- PPTX/PDF 最终可下载时间。
- 总耗时、模型调用次数、token 使用、重试次数和失败阶段。
- 页面生成、渲染、审稿、修复和导出的 p50/p95 耗时。

验收标准：

- 形成可重复的阶段耗时报告。
- 优化前后使用同一测试集对比质量和速度。
- 完整生成成功率不下降，导出文件可正常打开。
- 相同内容页面不会重复渲染、重复审稿或重复完整导出。
- 同一问题连续无进展时能够及时停止并保留可编辑稿。
- 快速模式与专家模式共享底层能力，不复制渲染、审稿和导出实现。
- 性能目标在实际基线测量后确定，不预先承诺无依据的百分比。

- 版本冲突、取消、恢复和失败不发布行为已有自动化覆盖。

已确认的架构决策：

- 保留快速模式和专家模式两个产品入口。
- 两种模式采用统一的编排主干和共享服务。
- 模式差异通过 Execution Policy 表达，不能复制生成、渲染、审稿和导出实现。
- 优先采用模块化单体，不在一开始拆分微服务。
- 将生成、审稿和导出并发池分离，解决资源互相阻塞。
- 统一页面状态、问题指纹、检查点、版本和任务事件契约。

计划形成的模块边界：

- `orchestrator.py`：任务状态机、阶段执行、恢复和事件。
- `policies/quick.py`：快速模式策略。
- `policies/expert.py`：专家模式策略。
- `context_service.py`：模板、资料、公司知识库和研究。
- `model_gateway.py`：文本与视觉模型、token 预算、限流和重试。
- `page_work_queue.py`：页面 DAG、并发和页面状态。
- `render_service.py`：浏览器渲染与增量缓存。
- `review_service.py`：整稿和页面视觉审稿。
- `repair_coordinator.py`：问题聚合、定向修复和停滞检测。
- `export_service.py`：审稿渲染与最终交付导出。
- `pptd_store.py`：继续作为权威 PPTD 文档版本库。

其他需要设计的问题：

- 项目、文档版本、任务和产物的统一数据模型。
- 同步接口、异步任务、SSE 和恢复机制的统一契约。
- `PptdStudio.tsx` 中的大型视图和生成状态如何拆分。
- `kimi_agent.py` 如何缩减为专家策略、Agent 适配和工具边界。
- 模型、知识库和部署配置如何抽象为 provider。
- 渐进迁移的阶段、兼容层、切换点和回滚方案。

建议的重构顺序：

1. 消除重复渲染和重复完整导出。
2. 建立页面状态、问题指纹和修复停滞检测。
3. 做增量渲染和审稿缓存。
4. 拆分生成、审稿和导出并发池。
5. 视觉审稿按页受控并行。
6. 页面批次和并发根据模型能力自适应。
7. 优化上下文、前缀缓存和参考资料复用。
8. 增加草稿预览和阶段耗时指标。
9. 抽取统一 Orchestrator 和两种 Execution Policy。
10. 收敛旧路线和重复模块。

验收标准：

- 先形成架构决策记录和迁移计划，再开始编码。
- 重构步骤可独立发布、测试和回滚。
- 不在重构过程中丢失现有项目、版本和导出能力。
- 快速模式和专家模式继续独立可选，但共享同一套底层服务。
- 任务执行状态与实际阶段一致，能够观察到每个阶段的真实耗时。

## 总体验收原则

- 任何自动生成或自动修复都必须保留版本，不允许无提示覆盖用户成果。
- 外部模型、知识库和搜索引擎不可用时必须显式降级，不伪造结果或引用。
- 生成成功的标准是最终 PPTX/PDF 可打开且关键内容正确，不能只看模型返回。
- 功能、部署和离线能力都必须有可重复的测试或验收步骤。
- 运行产物、密钥和用户数据不进入 Git。
